Introduction

While working on the syscall-smuggler CTF challenge, the main restriction was that the shellcode could not contain syscall, sysenter, or int instructions.

The challenge reads the supplied bytes, applies a filter, and then executes them as code. The filter searches for specific byte sequences corresponding to system-call instructions.

Honestly, I don't know why, but I got kind of obsessed with this challenge. I kept experimenting with the shellcode and the instruction bytes until I finally figured out how to make it work.

So yeah, I just felt like sharing this with you guys. It's a small thing, but I really enjoyed figuring out how the bytes could be changed at runtime and still execute as a syscall.

The main objective was to execute system calls without having the corresponding instructions present when the shellcode was scanned.

1. Challenge Restriction

The filter checks for the following byte sequences: 

0F 05  → syscall
0F 34  → sysenter
CD 80  → int

Therefore, directly placing the following instruction in the shellcode would cause the filter to reject it: 

0F 05

The challenge therefore required a different approach.



2. The Basic Idea

Instead of storing the syscall instruction directly, I used a two-byte placeholder. 

dw 0x9090

The resulting bytes are: 

90 90

These bytes represent two NOP instructions and do not match the forbidden 0F 05 sequence.

The important part is that the placeholder is modified later during execution.



3. Self-Modifying Code

A small section of the shellcode modifies the placeholder before it is executed. 

add word [first_syscall], 0x747F

Initially the memory contains: 

90 90

The 16-bit calculation is: 

0x9090 + 0x747F = 0x1050F

Because the destination is a 16-bit word, only the lower 16 bits are stored: 

0x050F

x86 uses little-endian byte ordering, so the bytes in memory become: 

0F 05

The resulting instruction is: 

0F 05 = syscall

Therefore, the transformation is: 

90 90
  |
  v
0F 05


4. Why the Filter Does Not Detect It

The important point is that the filter scans the shellcode before the self-modifying code executes.

During filtering, the bytes are: 

90 90

The forbidden sequence: 

0F 05
does not exist yet.

After the filter finishes, the shellcode executes the modification code and changes the bytes in memory.

5. Multiple Syscall Locations

The shellcode requires multiple system calls, so multiple placeholders were created. 

first_syscall:
    dw 0x9090

second_syscall:
    dw 0x9090

The same modification technique is then applied to each location. 

add word [address], 0x747F

Each placeholder is transformed into: 

0F 05

This allows multiple system calls to be executed without placing the forbidden instruction bytes directly into the initial shellcode.

6. Preparing the System Calls



After creating the runtime syscall instructions, the shellcode prepares the required Linux system-call arguments using the x86-64 Linux syscall ABI.

6.1 Open

The syscall number for open is prepared using: 

xor eax, eax
mov al, 2

This results in: 

RAX = 2

The filename address is passed through RDI before the generated syscall instruction is executed.

6.2 Read

The file descriptor returned from the previous operation is moved into RDI. The buffer address is placed in RSI, while the number of bytes to read is placed in RDX.

The read syscall number is: 

RAX = 0

The runtime-generated syscall instruction then performs the read operation.

6.3 Write

The write syscall uses: 

RAX = 1
RDI = 1

Here, RAX = 1 represents the write syscall and RDI = 1 represents standard output.

The number of bytes returned by the previous read operation is used as the write length.

6.4 Exit

Finally, the shellcode prepares the exit syscall: 

mov al, 60

This gives: 

RAX = 60

The final generated syscall terminates the process.

8. The Important Trick

The key observation was that the filter checks the initial bytes of the shellcode rather than continuously monitoring the memory during execution.

Because of this, the shellcode can initially contain: 

90 90

and later transform those bytes into: 

0F 05

The executed instruction is therefore different from the instruction bytes that were originally inspected by the filter.

The shellcode does not contain the syscall instruction initially; it constructs the instruction at runtime.

9. Conclusion

This challenge was a practical example of self-modifying shellcode. The main technique was to use harmless placeholder bytes and transform them into the required instruction only after the filtering stage.

The important transformation was: 

90 90
  |
  v
0F 05

This allowed the shellcode to pass a byte-based filter while still executing the required system calls at runtime.

The main lesson from this challenge was understanding the difference between the static bytes inspected by a filter and the instructions that exist when the processor actually executes the code.

10. Polymorphic Aspect

This approach is closely related to the concept of polymorphic shellcode. Polymorphic shellcode changes the byte-level representation of code while preserving its intended behaviour.

In this challenge, the shellcode does not contain the final syscall instruction in its initial representation. Instead, a different byte sequence is placed at the syscall locations and modified during execution. 

Initial Representation

90 90

After the runtime transformation, the same location becomes: 

0F 05

Therefore, the bytes inspected by the filter are different from the instruction bytes that are eventually executed by the processor.

The important idea is to change the representation of the instruction at runtime while preserving the intended behaviour of the shellcode.

More precisely, this implementation is an example of self-modifying shellcode and runtime instruction generation. It has a polymorphic characteristic because the static byte representation and the runtime representation are different, but it is not a complete traditional polymorphic encoder/decoder by itself.
